# NANOREM — реестр проектных решений

Дата актуализации: 14 октября 2026 года.

## 1. Назначение документа

Этот документ — единый источник актуальных бизнес-решений NANOREM. Дальнейшая разработка должна опираться на него, а не на историю переписки или устаревшие документы.

В документе раздельно ведутся четыре категории сведений:

| Категория | Значение |
|---|---|
| Утверждено | Решение явно подтверждено владельцем проекта. Обязательно для реализации. |
| Текущее поведение кода | Так работает код по результатам аудита. Это не обязательно утверждённое бизнес-правило. |
| Открытый вопрос | Требует решения владельца или согласования с производителем. |
| Запланировано | Возможность нужна в будущем, но ещё не реализована. |

### Приоритет источников

1. Явно утверждённые решения из раздела 2 этого документа.
2. Более поздние подтверждённые решения, внесённые в этот документ с датой.
3. Старые документы из папки `docs/` — источник исторической информации.

Если старый документ или код противоречит утверждённому решению, приоритет имеет утверждённое решение. Расхождение нельзя устранять молча: его нужно внести в раздел 3 или раздел 8, разобрать и закрыть отдельным решением.

### Правила ведения

- Новое решение вносится с датой и указанием, кем оно утверждено.
- Утверждённое решение не меняется задним числом. Изменение оформляется новой записью со ссылкой на прежнюю.
- Старые документы не удаляются и не переписываются без отдельного решения владельца.

## 2. Утверждённые правила MLM

Статус правил R-1 — R-7: **утверждены владельцем проекта 10.10.2026**, с учётом более поздних дополнений в разделе 10.

Эти правила нельзя расширять или изменять без нового явного решения владельца.

**R-1. Пять оплачиваемых уровней.**

Маркетинговый план предусматривает пять оплачиваемых уровней: 20%, 10%, 5%, 5%, 5%.

**R-2. Два постоянных Root.**

В системе существуют два постоянных Root-партнёра. Их создаёт администратор. Публичная регистрация не должна создавать Root.

**R-3. Регистрация только по реферальному коду — историческая редакция от 10.10.2026.**

Первоначальная редакция правила требовала действительную реферальную ссылку или код для публичной регистрации нового партнёра. Нельзя принимать произвольный `partner_id` вместо реферального кода.

Изменение этого правила оформлено отдельным датированным дополнением в разделе 10. Старый текст сохранён для истории и не должен трактоваться отдельно от более позднего решения.

**R-4. Root всегда активны.**

Два Root являются создателями системы и всегда активны независимо от покупок, подписки и даты её окончания.

**R-5. Root не сжимаются и получают комиссии.**

Root не подвергаются структурной compression. Root имеют право получать обычные MLM-комиссии, когда попадают в оплачиваемые уровни действующего пятиуровневого плана.

**R-6. Поздняя реактивация — под первоначальный Root.**

При поздней реактивации партнёр размещается непосредственно под своим первоначальным Root: `upline_id = root_id`. Не следует искать другого родителя, выбирать лучшее место или балансировать размещение в этой ветке.

**R-7. Область действия правила R-6.**

Правило R-6 относится только к подтверждённой реактивации. Этот документ не утверждает, что любая покупка автоматически восстанавливает активность партнёра. Условия, при которых реактивация считается подтверждённой, определяются правилами активности (см. раздел 8, вопросы Q-1 и Q-2).

### Требование к реализации R-4 и R-5

Постоянная активность и защита Root от compression должны быть реализованы как системный инвариант. Это не настраиваемый коммерческий параметр, его нельзя отключить через версии правил.

## 3. Текущая реализация — отдельно от бизнес-решений

Статус раздела: **Текущее поведение кода**.

Сведения ниже включают результаты предварительного аудита в октябре 2026 года. Часть первоначальных выводов получена чтением кода без запуска. Результаты последующих проверок указаны отдельно. Не следует считать все пункты повторно проверенными только потому, что они перечислены в этом документе.

### Известные расхождения с утверждёнными правилами и открытые места

**D-1. Root в первоначальном аудите кода неактивен.**

Первоначальный аудит обнаружил противоречие с R-4 и R-5.

- `services/partner_service.py`, `create_root`: Root создавался с `subscription_end_date=None`.
- `database/models.py`, свойство `Partner.is_active`: партнёр без срока подписки считался неактивным. Особого случая для Root в проверенной тогда версии не было.
- `services/subscription_service.py`, `apply_purchase`: для Root (`root_id == id`) подписка не продлевалась.
- `core/commission.py`, `_build_compressed_chain`: неактивные партнёры пропускались в цепочке комиссий.
- Вывод первоначального аудита: Root, созданный через `create_root`, мог не получать комиссии.
- Защита Root от compression была обнаружена в `expire_due_partners` и `compress_partner` (`services/structural_compression_service.py`).

Этот пункт отражает результаты первоначального аудита. При дальнейших изменениях фактическое поведение необходимо сверять с актуальным кодом и тестами.

**D-2. В первоначальном аудите тестов Root искусственно активен.**

- `tests/test_structural_compression_recovery.py` (функция `_tree`) и `tests/test_commission_5levels.py` создавали Root вручную со сроком подписки +365 дней.
- Поэтому тесты могли ожидать, что Root получает уровни, даже если рабочий `create_root` не обеспечивал активность.
- Первоначальный аудит не обнаружил тестов, в которых настоящий Root из `create_root` стоял в цепочке комиссий.

**D-3. Пороги активности.**

Это текущее поведение кода, а не утверждённое правило.

- `services/subscription_service.py`.
- Месячная активность: покупка ровно на 3 000,00 руб. (`MONTHLY_PURCHASE_AMOUNT`) даёт +1 календарный месяц.
- Годовая активность: разовая покупка от 10 000,00 руб. (`ANNUAL_PURCHASE_AMOUNT`) или накопление 10 000,00 руб. в пределах одного календарного месяца даёт 12 месяцев.
- Покупки на другие суммы активность не продлевают.
- Во время годовой активности продление не выполняется.
- В расчёт входит полная сумма заказа, включая часть, оплаченную балансом.
- Исторический источник: `MLM_Architecture_and_Payouts.md` («Варианты входа: 10 000 руб. … 3 000 руб.»).

**D-4. Автоматическое распределение новых партнёров между Root.**

В первоначальном аудите было зафиксировано следующее:

- `services/distribution_service.py`: выбирается Root, у которого меньше потомков; при равенстве — Root с большим `id`.
- Этот механизм использовался в `services/order_processor.py`, `_choose_root_for_new_partner`.
- В первоначальном аудите публичная регистрация (`/register` в `web/app.py`) не использовала `PartnerService.choose_root`.
- Критерий балансировки по размеру сети на тот момент отдельно не был утверждён.

**Актуализация по результатам проверок 14.10.2026:**

- В проверенном `services/partner_service.py` метод `choose_root()` делегирует выбор в `DistributionService().get_upline_for_new_partner(session)`.
- `services/order_processor.py`, `_choose_root_for_new_partner`, также делегирует выбор в `DistributionService`.
- Поиск по `services`, `web` и `tests` показал один алгоритм балансировки — в `services/distribution_service.py`.
- Правило выбора: Root с меньшей сетью; при равенстве — Root с большим `id`.
- Целевой набор `tests/test_distribution.py` завершился результатом **8 passed**.
- Регистрация без `ref` и регистрация с действительным `ref` успешно проверены на изолированной тестовой базе.

Эти результаты относятся к выполненным локальным проверкам. Они не являются доказательством проверки production.

**D-5. Создание партнёра из заказа WooCommerce без реферального кода.**

- `services/order_processor.py`, `_find_or_create_partner`.
- Если email покупателя не найден среди партнёров, создаётся новый партнёр под Root, выбранным по D-4.
- Цепочка вызова: `POST /webhook` (`web/app.py`) → `process_webhook` → `process_order_data` → `_find_or_create_partner`.
- Допустимость автоматического создания партнёра при заказе WooCommerce без реферального кода требует отдельного решения (вопрос Q-4).

**D-6. Вознаграждение создателя системы не реализовано.**

Первоначальный аудит не обнаружил соответствующего кода.

### Другие замечания аудита, связанные с правилами

Эти пункты отражают результаты первоначального чтения кода и не должны считаться повторно проверенными без нового основания.

- **D-7. Создание Root в production.** В первоначальном аудите создание Root было обнаружено через `/create-root` в `web/order_handler.py`, при `DEBUG=True` и с заголовком `X-Admin-Secret`. Маршрут был подключён только в `main.py`.
- **D-8. Роль администратора.** В первоначальном аудите `PartnerRole.ADMIN` была объявлена в `database/models.py`, но серверные проверки прав по ней обнаружены не были. Страница `/dashboard` отдавалась без серверной проверки авторизации.
- **D-9. Конфликт восстановления.** В первоначальном аудите `RecoveryConflictError` при восстановлении структуры приводил к откату обработки заказа и ответу HTTP 500 (`services/order_processor.py`, `process_order_data`; `web/app.py`, `/webhook`).

- **D-11. Ставки и ранги в старых документах.** `NEXT_STEPS.md` (п. 1) содержит «проценты зависят от ранга». Это противоречит R-1 и считается исторической информацией.

## 4. Коммерческие правила, которые планируется сделать настраиваемыми

Статус раздела: **Запланировано**. Это требование к будущей архитектуре, а не описание реализованной функции. Перечисленные значения могут быть зашиты в коде (см. раздел 3).

### Что должно настраиваться без переписывания бизнес-логики

- Пороги ежемесячной и годовой активности.
- Правила суммирования покупок.
- Ставки и параметры MLM-комиссий, если соответствующие изменения будут утверждены. Действующие ставки — R-1.
- Критерии получения званий и их срок действия.
- Условия начисления будущего вознаграждения создателю системы.
- Условия, даты и ограничения акций.

### Что не настраивается

Системные инварианты не входят в настраиваемые параметры и меняются только новым решением владельца с изменением кода:

- R-2 — R-7 с учётом датированных дополнений;
- постоянная активность Root и защита Root от compression.

### Принцип версионирования правил

- Коммерческие правила хранятся отдельно от кода и от секретов.
- Новая версия правил создаётся как черновик, утверждается и получает дату вступления в силу.
- Утверждённая версия не изменяется. Изменение оформляется новой версией.
- Исторические начисления не пересчитываются автоматически по новым условиям.
- Каждое начисление должно позволять определить версию правил, по которой оно рассчитано.
- Изменения версий фиксируются в журнале аудита: кто, когда, что изменил и кто утвердил.
- Изменение финансовых параметров допускается только после появления серверной проверки прав администратора, журнала аудита и предварительной симуляции последствий.

## 7. Модуль акций

Статус раздела: **Запланировано**.

В будущем нужно предусмотреть:

- включение и выключение акции;
- даты начала и окончания;
- условия участия и целевую аудиторию;
- виды выгоды и лимиты использования;
- совместимость с другими акциями;
- учёт применённых акций, повторных webhook, отмен и возвратов;
- сохранение версии условий, по которым акция применялась к конкретному заказу.

Ограничения:

- Конкретные скидки, бонусы, бюджеты и сроки этим документом не назначаются.
- Влияние акций на активность партнёра, оборот, пять линий комиссий, ранги и вознаграждение создателя требует отдельных решений (вопросы Q-7 и Q-9).
- Перед реализацией акций нужна корректная разбивка заказа: стоимость товаров, скидка, доставка, итог, оплата деньгами, оплата балансом. В первоначальном аудите обработка заказа использовала только итоговую сумму `total` (`services/order_processor.py`).
- Сложные типы акций не реализуются до согласования их финансовой базы.

### Решение владельца от 14.10.2026 — пороги активности

Это дополнение к реестру. Записи D-3 и раздел 4 не переписываются.

Владелец утвердил:

- отдельная оплаченная покупка не ниже месячного порога даёт месяц активности, если годовое условие не выполнено;
- сумма оплаченных покупок за один календарный месяц не ниже годового порога даёт годовую активность;
- разовая оплаченная покупка не ниже годового порога даёт год и имеет приоритет;
- начальные значения: `MONTHLY_PURCHASE_AMOUNT` 3000.00 руб. и `ANNUAL_PURCHASE_AMOUNT` 10000.00 руб.;
- пороги читаются из окружения и применяются после перезапуска приложения.

Это временный механизм настройки двух порогов. Он не реализует версионирование коммерческих правил из раздела 4.

Этим решением не утверждались оплата балансом, возвраты, даты начала и продления, постоянная активность Root и поведение при уже действующей годовой активности.

## 10. Дополнение от 13 октября 2026 года — регистрация без реферального кода

**Статус: утверждено владельцем проекта 13.10.2026.**

Это дополнение изменяет прежнее правило R-3 в части обязательности реферального кода. Исторический текст R-3 в разделе 2 сохранён и не удаляется.

### 10.1. Новое правило публичной регистрации

Публичная регистрация должна работать как с действительным реферальным кодом, так и без него.

1. Если передан действительный реферальный код, новый партнёр размещается согласно этому коду.
2. Если реферальный код не передан, система автоматически выбирает одного из двух существующих Root с балансировкой сети.
3. Публичная регистрация не создаёт Root автоматически.
4. Произвольный числовой `partner_id` не принимается вместо действительного реферального кода.
5. Для нового партнёра должны быть согласованно сохранены `upline_id`, `root_id` и `lineage`.
6. Ошибка при создании партнёра не должна оставлять частично сохранённую структуру.

### 10.2. Единый алгоритм выбора Root

Для автоматического размещения используется единый канонический механизм `DistributionService.get_upline_for_new_partner(session)`.

Правило выбора:

- выбирается Root с меньшим количеством потомков;
- если размер сетей одинаков, выбирается Root с большим `id`;
- система должна работать ровно с двумя существующими Root;
- отдельные реализации алгоритма балансировки в других сервисах не допускаются. Другие сервисы должны вызывать канонический механизм, а не повторять его логику.

Правило поздней реактивации R-6 не меняется: реактивированный партнёр размещается непосредственно под первоначальным Root, а не перераспределяется балансировкой.

### 10.3. Проверки и подтверждённое состояние на 14 октября 2026 года

По результатам проверок, выполненных на изолированной тестовой базе:

- регистрация без `ref` прошла успешно;
- регистрация с действительным `ref` прошла успешно;
- целевой набор `tests/test_distribution.py` завершился результатом `8 passed`;
- проверка вызовов распределения показала, что `PartnerService` и `OrderProcessor` используют `DistributionService`, а не отдельные алгоритмы выбора Root;
- вход, выход и повторный вход проверялись на тестовой базе.

Эти результаты не доказывают корректность production и не означают, что все сценарии регистрации уже покрыты автоматическими регрессионными тестами.

Попытка повторно зарегистрировать уже использованный контакт вернула HTTP 400 с общим сообщением `Unable to create partner`. Это ожидаемый конфликт уникальности для дублирующегося контакта. Точное имя нарушенного ограничения для этого конкретного запроса не было установлено; причина не считается отдельной неисправностью регистрации без дополнительных доказательств.

### 10.4. Требуемые регрессионные тесты

Должны быть покрыты следующие сценарии:

1. Публичная регистрация без `ref` создаёт обычного партнёра под одним из двух существующих Root.
2. Повторная регистрация без `ref` балансирует размещение по размеру сетей.
3. При равенстве сетей выбирается Root с большим `id`.
4. Регистрация с действительным `ref` размещает партнёра согласно реферальному коду.
5. Публичная регистрация не создаёт третьего Root.
6. Произвольный `partner_id` не заменяет действительный реферальный код.
7. При ошибке создания партнёра незавершённые изменения откатываются.
8. `PartnerService` и `OrderProcessor` используют один канонический алгоритм распределения.

Результаты ручной проверки и автоматических тестов необходимо указывать раздельно.
